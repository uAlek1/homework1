# Homework 1
Полное задание представлено в [task.md](./task.md). Вычисление L1-нормы:
- `row` — обход по строкам;
- `column` — обход по столбцам;
- `avx` —  обход по строкам с использованием avx2.

# Сборка и запуск
Для сборки необходим cmake и компилятор для C++ (clang или g++).
```bash
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=release
cmake --build .
```

Программа работает в двух режимах. 

Первый режим генерирует квадратную матрицу и сохраняет ее в заданный файл.
Пример запуска:
```bash
./homework1 gen_matrix N low max output 
``` 
где:
- `N` - размер матрицы
- `low и max` - диапазон случайных чисел, которыми заполняется матрица 
- `output` - выходной файл, куда записывается матрица

Второй режим вычисляет L1-норму квадратной матрицы.
Пример запуска:
```bash
./homework1 test matrix type 
``` 
где:
- `matrix` - путь до файла с матрицей
- `type` - тип обхода, row - по строкам, column - по столбцам, avx - по строкам с использованием avx2

# Аппаратное доказательство оптимальности
Из полученных результатов была собрана следующая таблица

|---|---|---|---|---|---|
| Column    | 602,775,873 | 26,315,475 | 832,104,809 | 1,838,849,373 | 0.45
| Row       | 581,569,218 | 11,358,204 | 825,605,976 | 832,573,436   | 0.99

| Read file | 246,294,765 | 9,272,965  | 390,225,085 | 27,968,788    | 0.62

Согласно официальным руководствам AMD по оптимизации (Software Optimization Guide for AMD Family 17h Processors, смотри /doc) размер кэш-линии на моем процессоре 64 байта, что также подтверждается выводом команды `getconf LEVEL1_DCACHE_LINESIZE`.
Норма считалась для квадратной матрицы размером 4096 × 4096 элементов, каждый размером 8 байт. 
### Чтение по столбцам
При обходе по столбцам используется один элемент (8 байт) из всей загруженной кэш-линии. Остальные 56 байт в последствии вытесняются, так как они не используются до следующей итерации внешнего цикла. Таким образом, эффективность использования кэш-линии при обходе по столбцам составляет 8/64 = 12.5%, а объём бесполезно прокачанных данных = 87.5%. Суммарный объём данных для исходной матрицы: `4096 × 4096 × 64 = 1 073 741 824` байт
### Чтение по строкам
При обходе построчно используется вся загруженная кэш-линия. Минимальное число загрузок, когда каждая линия загружается один раз и используется полностью:
`4096 * 4096 * 8 / 64 = 2097152 `. Теоретически, разница в промахах кэша между чтением по столбцам и по строкам должна иметь отношение 8 к 1.

### Соответствие с полученными метриками
Дополнительно были сняты метрики для чтения файла с матрицей без вычисления нормы, в таблице это строка `Read file`. Соответственно, данные промахи не учитывались при вычислении отношения промахов кэша при вычислении построчно и по столбцам. ` (26,315,475 - 9,272,965) / (11,358,204 - 9,272,965) = 8.2, что соответствует теоретически рассчитанному коэффициенту.
### AVX2
AVX2-версия обхода по строкам использует 256-битные регистры (__m256i), обрабатывая по 4 элемента uint64_t за одну инструкцию, с развёрткой на 4 независимых аккумулятора. В полученных результатах это заметно по столбцу instructions, где заметно упало число выполняемых инструкций. Но поскольку AVX2 не снижает количество трафика, вычитываемого из памяти, cycles не уменьшается пропорционально instructions, из-за чего уменьшается метрика IPC. Но даже при этом, AVX2 дает выигрыш в производительности по сравнению с простым построчным вычислением. 
### Выводы
1) Последовательный проход оказывается оптимальным решением, поскольку каждая загрузка в кэш дает 100% полезной нагрузки, в то время как обход по столбцам дает 12,5%. Практически показано, что число кэш промахов при последовательном проходе меньше в ~8 раз, по сравнению с обходом по столбцам;
2) AVX2 интринсики уменьшают число выполняемых инструкций, выполняя операции сразу над 256-битными векторами. Однако здесь узким горлышком становится общение процессора с диском, из-за чего уменьшается IPC.
